# PlanMate 비동기 일정 생성 파이프라인 장애 복구 검증

> 포트폴리오 저장소 반영용 최종 원고  
> 기준일: 2026-08-29  
> 최종 결과: **7개 실험 모두 PASS**

## 1. 포트폴리오 첫 화면용 요약

### 비동기 일정 생성 파이프라인 장애 복구 검증 — 7개 실험 PASS

PlanMate는 사용자의 여행 요청을 DB에 안전하게 저장한 뒤, Debezium과 RabbitMQ를 거쳐 Worker가 장소 후보를 수집하는 비동기 구조다. 이 과정에서는 구성요소가 잠시 중단되거나 같은 메시지가 다시 전달될 수 있다.

이를 검증하기 위해 데이터 저장부터 Worker 처리 완료까지의 주요 장애 경계에 실제 중단·재기동·재전달을 주입했다. 일곱 실험 모두 최종 상태 기준으로 **이벤트 유실 0건, 후보 데이터 중복 0건**을 확인했다. 단, 이 결과는 로컬 Docker 기반의 재현 가능한 실험 환경에 대한 결과이며 모든 운영 장애를 보장한다는 의미는 아니다.

### 핵심 설계 한 문장

**Transactional Outbox와 Debezium은 커밋된 이벤트가 전달 경로에 남도록 하고, RabbitMQ의 ACK·재전달과 Worker의 상태·Claim Version·DB 제약 조건은 중복 전달이 최종 데이터 중복으로 이어지지 않도록 한다.**

Debezium 하나가 서비스 간 멱등성을 보장하는 것은 아니다. 여러 장치가 각자의 장애 구간을 맡아 함께 복구 가능성과 결과 멱등성을 만든다.

## 2. 독자가 먼저 이해해야 할 처리 흐름

```text
사용자 요청
  ↓
API 트랜잭션
  ├─ Generation 저장
  ├─ 입력 Snapshot 저장
  └─ Outbox Event 저장
  ↓
Debezium CDC
  ↓
RabbitMQ 발행·전달
  ↓
Worker가 메시지 수신
  ↓
DB Claim 획득
  ↓
장소 후보 수집·DB 반영
  ↓
RabbitMQ ACK
```

여기서 API와 Worker는 서로 다른 프로세스로 실행했다. 포트폴리오에서는 검증하지 않은 배포 형태를 확대 해석하지 않도록 “두 마이크로서비스”보다는 **API 프로세스와 Worker 프로세스**라고 표현한다.

### 쉬운 용어 설명

| 표시명 | 내부 상태·용어 | 의미 |
| --- | --- | --- |
| 전달 대기 | `CREATED` | 요청과 Outbox는 DB에 저장됐고 Worker 전달을 기다리는 상태 |
| 후보 수집 중 | `COLLECTING_CANDIDATES` | Worker가 해당 작업의 처리 권한을 얻고 후보를 수집하는 상태 |
| 후보 수집 완료 | `READY_FOR_PLANNING` | 후보 저장을 마쳐 다음 일정 생성 단계로 갈 수 있는 상태 |
| Claim | Claim Version | 여러 Worker 중 누가 현재 결과를 저장할 권한이 있는지 나타내는 번호 |
| ACK | RabbitMQ Acknowledgement | Worker가 처리를 끝냈다고 Queue에 알리는 확인 신호 |
| SKIP | 멱등 처리 | 이미 끝난 이벤트가 다시 오면 다시 저장하지 않고 안전하게 건너뜀 |
| Fencing | 오래된 Worker 결과 차단 | 처리 권한을 잃은 Worker가 뒤늦게 결과를 저장하지 못하게 막음 |

## 3. 일곱 실험이 검증한 장애 경계

실험 번호는 실행 순서이고, 아래 표는 **실제 비동기 처리 순서**에 맞춰 다시 배치한 것이다.

| 처리 경계 | 관련 실험 | 검증 질문 | 결과 |
| --- | ---: | --- | --- |
| DB Commit → CDC 재개 | 1 | Debezium이 멈춘 동안 저장된 Outbox가 재기동 후 전달되는가 | PASS |
| Debezium → RabbitMQ | 6 | Broker가 멈춰 발행하지 못한 이벤트가 복구 후 전달되는가 | PASS |
| RabbitMQ 전달 → DB Claim | 7 | 전달만 받고 선점하기 전에 Worker가 죽어도 다른 Worker가 처리하는가 | PASS |
| Worker 처리 중 실패 | 4 | 재시도 가능한 실패와 불가능한 실패가 다르게 처리되고 DLQ에 격리되는가 | PASS |
| Claim → 장기 정지 → 새 Claim | 5 | 멈춘 Worker의 권한을 회수하고 뒤늦은 결과를 차단하는가 | PASS |
| DB 결과 Commit → RabbitMQ ACK | 2 | DB 반영 후 ACK 전에 죽어 재전달돼도 결과가 중복되지 않는가 | PASS |
| CDC Checkpoint 불일치·과거 이벤트 Replay | 3 | 이미 처리한 이벤트가 CDC에서 다시 발행돼도 최종 결과가 중복되지 않는가 | PASS |

이 일곱 실험은 현재 로컬 아키텍처에서 정의한 **주요 실패 경계**를 검증한다. 각 구성요소의 모든 내부 장애, 네트워크의 모든 형태, 운영 환경의 부하와 다중 노드 장애까지 검증했다는 뜻은 아니다.

## 5. 실험별 포트폴리오 카드 원고

각 카드는 `검증 질문 → 실제 장애 주입 → 관측 결과 → PASS 이유 → 한계` 순서로 사용한다. 포트폴리오 본문에는 핵심 이미지 2~3장만 넣고 전체 Grafana·DB·RabbitMQ 증거는 GitHub 링크로 연결한다.

### 실험 1. Debezium 중단 후 재시작

**검증 질문**  
Debezium이 멈춘 동안에도 사용자 요청을 DB에 저장할 수 있고, 재기동 후 밀린 Outbox 이벤트가 유실 없이 전달되는가?

**실제 장애 주입**  
Debezium 컨테이너를 중단한 상태에서 여행 요청 10건을 생성한 뒤, Outbox 적재와 Queue 미전달 상태를 확인하고 컨테이너를 재기동했다.

**관측 결과**

- Outbox 생성: 10건
- RabbitMQ 발행/전달/ACK: 10/10/10건
- `READY_FOR_PLANNING`: 10/10건
- 후보 데이터: 1,200건
- 이벤트 유실·DLQ 증가: 0건
- Connector 상태 복구: 9.818초
- 전체 적체 처리 완료: 37.323초

**왜 PASS인가**  
중단 중 Queue 전달은 멈췄지만 DB에 커밋된 Outbox 10건은 사라지지 않았다. Debezium 재기동 후 동일한 10건이 전달되고 Worker가 전부 완료했다.

**한계**  
로컬 단일 Debezium 컨테이너의 일시 중단을 검증한 결과다. 장시간 장애, 디스크 손상, 다중 Connector 장애까지 보장하지 않는다.

### 실험 2. DB 반영 후 ACK 이전 Worker 강제 종료

**검증 질문**  
Worker가 DB 결과를 저장한 뒤 RabbitMQ ACK를 보내기 전에 종료되어 같은 메시지가 다시 와도 후보가 중복 저장되지 않는가?

**실제 장애 주입**  
Worker가 한 작업의 후보 120건을 DB에 커밋한 직후 ACK 전 대기 지점에서 프로세스를 강제 종료하고 새 Worker를 실행했다.

**관측 결과**

- 종료 전 Queue: Ready 9, Unacked 1
- RabbitMQ 발행/전달/ACK: 10/11/10건
- RabbitMQ 재전달: 1건
- 완료 상태 확인 후 SKIP: 1건
- 최종 READY: 10/10건, 후보 1,200건
- 재큐잉 4.063초, Worker Health 복구 13.425초, 적체 해소 17.617초
- 유실·후보 중복·DLQ 증가: 0건

**왜 PASS인가**  
ACK를 못 받은 RabbitMQ가 한 메시지를 다시 전달했지만, Worker는 DB에 이미 완료된 Generation임을 확인하고 다시 후보를 저장하지 않았다.

**한계**  
정확한 종료 시점을 재현하기 위해 실험용 ACK 전 대기 Hook을 사용했다. 모든 종류의 JVM 종료 시점을 검증한 것은 아니다.

### 실험 3. CDC Offset 불일치와 과거 이벤트 재전달

**검증 질문**  
CDC Checkpoint가 어긋나 이미 처리한 Outbox 이벤트가 다시 발행돼도 최종 결과가 중복되지 않는가?

**실제 장애 주입**  
본 실험용 CDC 경로에서 저장된 위치와 PostgreSQL Replication Slot의 위치 불일치를 만들고, 과거 이벤트 10건을 다시 발행했다.

**관측 결과**

- 원본 이벤트: 10건
- 다시 발행된 과거 이벤트: 10건
- 논리적으로 중복된 이벤트: 10건
- RabbitMQ `redelivered=true`: 0건
- Worker SKIP: 10건
- READY: 재전달 전후 모두 10건
- 후보 데이터: 재전달 전후 모두 1,200건
- 불일치 감지 7.637초, Detector 복구 7.393초, Replay 완료 10.727초

**왜 PASS인가**  
CDC가 같은 논리 이벤트를 새 메시지로 다시 발행했지만, Worker가 완료 상태를 확인해 10건 모두 건너뛰었다. 후보 데이터 수는 증가하지 않았다.

**한계**  
실제 운영 Offset 저장소 손상을 일으킨 것이 아니라, 재현 가능한 실험용 CDC Connector와 Replay 경로로 불일치를 검증했다.

### 실험 4. Retry 분류와 DLQ

**검증 질문**  
일시적인 오류만 정해진 횟수만큼 재시도하고, 요청 자체가 잘못된 오류는 즉시 실패시킨 뒤 두 경우 모두 DLQ로 격리되는가?

**실제 장애 주입**  
항상 재시도 가능한 오류를 반환하는 요청 10건과, 항상 재시도하면 안 되는 오류를 반환하는 요청 10건을 분리 실행했다.

**관측 결과**

- Retryable 10건: 총 시도 30회, Retry 20회, 최종 FAILED 10건
- Retryable 오류 코드: `PLACE_PROVIDER_UNAVAILABLE`
- Non-Retryable 10건: 총 시도 10회, Retry 0회, 최종 FAILED 10건
- Non-Retryable 오류 코드: `PLACE_PROVIDER_REQUEST_REJECTED`
- 실험 DLQ: 0 → 10 → 20건
- 기존 운영용 DLQ: 167 → 167건으로 변화 없음
- READY·후보 데이터: 두 시나리오 모두 0건

**왜 PASS인가**  
오류 분류에 따라 실제 시도 횟수가 기대값과 정확히 일치했고, 최종 실패 메시지는 정상 Queue를 막지 않고 실험용 DLQ에 격리됐다.

**한계**  
외부 장소 API 자체를 고장 낸 것이 아니라, 실패 종류와 횟수를 통제할 수 있는 실험용 Recommender로 정책을 검증했다.

### 실험 5. Worker 장기 정지와 Stale Generation 복구

**검증 질문**  
Worker A가 Claim을 얻은 뒤 오래 멈추면 Worker B가 작업을 회수할 수 있고, A가 뒤늦게 보낸 결과는 차단되는가?

**실제 장애 주입**  
Worker A가 10건을 Claim한 뒤 Lease가 만료될 때까지 정지시켰다. 복구 Scheduler와 Worker B가 새 Claim으로 작업을 완료한 후 A를 다시 움직여 오래된 결과 저장을 시도했다.

**관측 결과**

- 최초 Claim: 10건
- 만료된 Lease: 10건
- 복구 메시지·새 Claim·Worker B 성공: 각각 10건
- Worker A의 늦은 결과 차단: 10건
- Worker A SKIP: 10건
- RabbitMQ 발행/전달/ACK: 20/20/20건
- READY: 10/10건, 후보: 1,200건
- Worker B 시작 후 READY 13.687초
- Lease 만료 후 복구 완료 13.688초
- READY 후 늦은 결과 차단 관측 91.627초
- 유실·후보 중복·실험 DLQ: 0건

**왜 PASS인가**  
Lease가 끝난 오래된 Claim은 저장 권한을 잃었다. Worker B의 새 Claim만 최종 결과를 반영했고, Worker A의 늦은 결과 10건은 Fencing으로 차단됐다.

**한계**  
실험용 대기 지점으로 장기 처리를 재현했다. 실제 외부 API가 여러 분 동안 응답하지 않는 모든 양상을 검증한 것은 아니다.

### 실험 6. RabbitMQ 중단과 CDC 복구

**검증 질문**  
RabbitMQ가 멈춰 Debezium이 메시지를 발행하지 못해도 DB의 Outbox가 남고, Broker 복구 후 10건이 모두 전달되는가?

**실제 장애 주입**

**관측 결과**

### 실험 7. RabbitMQ 전달 후 DB Claim 전 Worker 강제 종료

**검증 질문**  
Worker가 메시지를 받았지만 DB에서 처리 권한을 얻기 전에 종료되면, 재큐잉된 메시지를 새 Worker가 처음부터 처리할 수 있는가?

**실제 장애 주입**  
Worker A가 한 메시지를 전달받은 직후 Claim 전에 대기하도록 하고 프로세스를 강제 종료했다. RabbitMQ 재큐잉을 확인한 뒤 Worker B를 실행했다.

**관측 결과**

- 종료 전 상태: CREATED 10, COLLECTING 0, READY 0, 후보 0
- 종료 전 Queue: Ready 9, Unacked 1
- 종료 후 Queue: Ready 10, Unacked 0
- RabbitMQ 발행/전달/ACK: 10/11/10건
- RabbitMQ 재전달: 1건
- 최초 Claim: 10건
- SKIP: 0건
- READY: 10/10건, 후보: 1,200건
- 재큐잉 4.563초, Worker Health 복구 11.955초, 적체 해소 14.074초

## 6. 숫자는 비슷하지만 의미가 다른 실험 2·3·7

세 실험 모두 “같은 작업이 다시 들어오는 상황”을 다루지만 재전달이 생긴 위치와 Worker의 행동이 다르다.

| 구분 | 실험 2 | 실험 3 | 실험 7 |
| --- | --- | --- | --- |
| 장애 시점 | DB 결과 Commit 후 ACK 전 | CDC Checkpoint 불일치 | Rabbit 전달 후 DB Claim 전 |
| 다시 들어온 이유 | ACK가 없어 RabbitMQ가 재큐잉 | CDC가 과거 이벤트를 새 메시지로 Replay | ACK가 없어 RabbitMQ가 재큐잉 |
| RabbitMQ 전달 수 | 11 | 본 Queue 10 + CDC Replay 10 | 11 |
| `redelivered=true` | 1 | 0 | 1 |
| Worker 판단 | 이미 완료됨 | 이미 완료됨 | 아직 시작하지 않음 |
| 처리 결과 | SKIP 1 | SKIP 10 | 최초 Claim 10, SKIP 0 |

따라서 “전달 11건”을 “데이터가 한 건 중복 저장됐다”라고 읽으면 안 된다. 전달 횟수는 늘었지만 세 실험 모두 최종 후보 중복은 0건이다.

## 8. 포트폴리오 최종 결론 문안

### 본문용

PlanMate의 비동기 일정 생성은 단순히 메시지를 한 번만 보내는 구조가 아니다. DB Commit 이후 CDC, Broker 전달, Worker Claim, 결과 Commit, ACK 사이에서는 언제든 재시도와 재전달이 발생할 수 있다. 그래서 이벤트 전달을 담당하는 Transactional Outbox·Debezium·RabbitMQ와, 결과 중복을 막는 상태 확인·Claim Version·Lease·Fencing·DB 제약을 함께 설계했다.

주요 실패 경계에 일곱 가지 장애를 실제로 주입한 결과 모든 실험이 PASS했다. 중단 중 생성된 이벤트는 복구 후 처리됐고, ACK 이전 종료와 CDC Replay에서는 같은 메시지가 다시 들어와도 후보가 중복되지 않았다. Claim 이전 종료는 새 Worker가 최초 처리로 이어받았고, 장기 정지 Worker의 늦은 결과는 차단됐다. 실패 유형별 Retry와 DLQ도 기대 횟수와 일치했다. 최종적으로 정상 완료 시나리오에서는 이벤트 유실 0건과 후보 중복 0건을 확인했다.

이 결과는 “절대 장애가 나지 않는다”는 주장이 아니라, **장애가 발생해도 어떤 데이터가 남고, 누가 다시 처리하며, 중복 결과를 어떻게 막는지 측정 가능한 증거로 설명할 수 있게 됐다**는 의미다.

### 면접에서 30초 설명용

“Debezium 자체가 멱등성을 보장한다고 보지는 않았습니다. Outbox와 Debezium은 DB에 커밋된 이벤트의 전달 가능성을 지키고, RabbitMQ는 ACK가 없으면 다시 전달합니다. 그래서 Worker 쪽에서 완료 상태, Claim Version, Lease, Fencing, DB Unique Constraint로 같은 메시지가 여러 번 와도 최종 결과가 한 번만 반영되게 했습니다. 이 구조를 DB Commit부터 ACK까지의 주요 경계로 나눠 일곱 번 실제 중단했고, 모두 PASS했으며 유실과 후보 중복은 0건이었습니다.”

## 9. 사용하면 안 되는 과장 표현

- `Debezium이 두 서비스 간 멱등성을 보장한다.`
- `Exactly-once 전달을 완벽하게 달성했다.`
- `비동기 처리의 모든 장애 구간을 검증했다.`
- `운영 환경에서도 장애 복구가 보장된다.`
- `전달 횟수가 입력 수와 다르면 데이터 중복이다.`
- `Transactional 어노테이션 하나로 분산 처리 전체의 원자성이 해결된다.`

대신 다음처럼 표현한다.

- `At-least-once 전달을 전제로 Worker 결과를 멱등하게 만들었다.`
- `현재 아키텍처에서 정의한 주요 실패 경계를 로컬 Docker 환경에서 검증했다.`
- `Grafana, RabbitMQ, DB, 로그와 result.json을 교차 검증했다.`
