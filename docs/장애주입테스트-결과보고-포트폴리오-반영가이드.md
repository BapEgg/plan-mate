## 1. 일곱 실험의 공통 포트폴리오 형식

각 실험은 포트폴리오와 기술 블로그에서 아래 순서를 동일하게 사용한다.

```text
검증 질문
→ 실험 가설과 PASS 기준
→ 장애 주입 조건
→ 장애 범위 이미지
→ 복구 과정 이미지
→ 기대값/실제값 비교
→ 최종 판정
→ 발견한 문제와 개선
→ 한계 및 원본 증거 링크
```

### 포트폴리오 본문에 넣을 이미지 3종

| 번호 | 이미지 역할 | 독자가 한눈에 알아야 하는 내용 |
| ---: | --- | --- |
| 1 | 장애 범위 | 어떤 구성요소만 장애였고 무엇은 정상 상태를 유지했는가 |
| 2 | 복구 과정 | 대기 중인 데이터가 어떤 상태를 거쳐 최종 처리됐는가 |
| 3 | 정량 판정 | 입력 수, 전달 수, 완료 수, 유실·중복·실패 수가 일치하는가 |

### 이미지 작성 원칙

- 내부 코드값 대신 사람이 이해할 수 있는 한글 표시명을 우선 사용한다.
- 장애 시작, 재기동, 복구 완료 시각을 이미지 또는 바로 옆 타임라인에 표시한다.
- 전체 누적값보다 실험 전후 증가량을 사용한다.
- 정상은 초록, 대기/주의는 주황, 처리 중은 파랑, 장애/실패는 빨강을 사용한다.
- `No data`가 있는 패널은 핵심 결과 이미지로 사용하지 않는다.
- 운영 대시보드는 별도 원본 증거로 남기며, 포트폴리오 본문에는 필요한 패널만 확대한다.

## 2. 공통 상태 용어

| 포트폴리오 표시 | 내부 코드 | 정확한 의미 |
| --- | --- | --- |
| 전달 대기 | `CREATED` | Generation·입력 스냅샷·Outbox 저장 완료, Worker 시작 전 |
| 장소 후보 수집 중 | `COLLECTING_CANDIDATES` | Worker가 Google Places 후보를 수집하고 저장하는 중 |
| 후보 수집 완료 | `READY_FOR_PLANNING` | 후보 데이터가 확정되어 AI 일정 생성을 시작할 수 있음 |
| 최종 일정 저장 완료 | `COMPLETED` | 검증된 AI 일정이 최종 저장됨 |
| 처리 실패 | `FAILED` | 비동기 후보 수집이 정책에 따른 처리 후 최종 실패함 |

`CREATED`는 단순한 “생성 중”이 아니다. 요청과 Outbox는 이미 DB에 저장됐고 Worker 전달을 기다리는 상태이므로 포트폴리오에서는 **전달 대기**라고 표시한다.

## 8. 실험 중 발견한 문제와 개선

### 8.1 ACK 관측 시점 문제

첫 자동 판정은 `FAIL`이었다. 마지막 Generation의 DB 상태가 후보 수집 완료로 바뀐 즉시 RabbitMQ를 조회해, Listener가 반환되어 ACK를 보내기 전인 메시지 3건을 포착했기 때문이다.

안정화 후 publish·deliver·ACK 증가 10건, Queue ready·unacked 0건을 확인했다. 따라서 시스템 복구 실패가 아니라 테스트 실행기의 관측 시점 문제로 판정했고, 실행기가 Generation 완료 후 Queue 안정화를 최대 30초 기다리도록 수정했다.

### 8.2 RabbitMQ Grafana 수집 설정 문제

실험 당시 Prometheus는 RabbitMQ 기본 `/metrics`를 수집했지만 Grafana 쿼리는 Queue별 `queue` 라벨을 요구해 RabbitMQ 패널에 `No data`가 표시됐다.

수정 내용:

- Prometheus 수집 경로를 `/metrics/per-object`로 변경
- Queue별 ready, unacked, DLQ 라벨 조회 확인
- publish, deliver, ACK 누적 카운터 패널 추가
- 운영용 대시보드와 포트폴리오용 실험 대시보드 분리

이번 실험의 RabbitMQ 판정은 실험 전·중·후 RabbitMQ Management API 원본값을 사용했으므로 정량 판정에는 영향이 없다.

### 실험 1 한계

- 로컬 Docker Desktop에서 수행한 10건 규모의 복구 정확성 실험이다.
- 대규모 트래픽 처리량이나 최대 복구 시간을 검증한 부하 테스트가 아니다.
- Prometheus 수집 간격이 15초라 Grafana DOWN/UP 시각에는 최대 약 15초의 관측 오차가 있다.
- 정확한 Connector 복구 시간 9.818초는 Debezium Health endpoint 폴링 기준이다.
- RabbitMQ 수치는 Queue 전체 누적 카운터 전후 차이이며, 실험 중 다른 요청을 실행하지 않아 테스트 트래픽을 분리했다.

### 복구 시간

### 문제 발견과 개선

> Generation 완료 직후 Queue를 조회하면 Listener ACK가 끝나기 전의 메시지를 포착해 일시적으로 실패 판정이 발생할 수 있었다. 테스트 실행기가 Generation 완료 후 Queue 안정화를 최대 30초 기다리도록 수정했다. 또한 RabbitMQ Queue별 지표가 보이지 않던 Prometheus 수집 경로를 `/metrics/per-object`로 변경했다.

### 한계

> 이 결과는 로컬 Docker 환경에서 10건을 사용한 복구 정확성 실험이다. 대규모 트래픽 처리량이나 운영 환경의 최대 복구 시간을 보장하는 부하 테스트는 아니다.

## 19. 현재 포트폴리오에 바로 사용할 수 있는 실험 2 문안

### 제목

`DB 반영 후 ACK 이전 Worker 강제 종료 — PASS`

### 한 문장 결론

> 첫 메시지의 DB 반영이 끝났지만 ACK 전인 순간 Worker를 강제 종료했다. RabbitMQ가 미확인 메시지를 다시 Queue로 돌려보냈고, 복구 Worker는 재전달 1건을 감지해 이미 완료된 작업을 SKIP했다. 최종 10/10건 완료, 이벤트 유실과 후보 중복은 0건이었다.

### 복구 시간

### 문제 발견과 개선

> ACK 직전 종료를 반복 재현하기 위해 기본값 0초인 Reliability Hook을 추가했고 API와 Worker를 분리했다. 재전달 여부를 직접 관측하도록 `redelivered` Metric을 추가했으며, 외부 장소 API는 결정적 실험 공급자로 격리했다. 기존 멱등 Claim 로직이 재전달을 SKIP해 중복 저장을 막는 것을 검증했다.

### 한계

> 이 결과는 로컬 Docker 환경의 10건 복구 정확성 실험이다. Candidate 수집은 외부 API를 제외한 결정적 실험 공급자를 사용했고, Prometheus 15초 수집 간격보다 짧은 Unacked 구간은 RabbitMQ Management API 스냅샷으로 검증했다.

## 20. 현재 포트폴리오에 바로 사용할 수 있는 실험 3 문안

### 제목

`CDC Offset 불일치 탐지와 과거 이벤트 재전달 — PASS`

### 한 문장 결론

> PostgreSQL replication slot보다 오래된 Debezium Offset를 주입하자 Connector가 7.637초 만에 읽을 수 없는 위치를 탐지하고 중단됐다. 검증된 최신 Offset로 복구한 뒤 같은 과거 이벤트 10건을 재전달했지만 Worker가 모두 SKIP하여 READY 10/10, Candidate 1,200행을 유지했고 유실과 중복은 0건이었다.

### 장애 시뮬레이션

> 폐기 가능한 PostgreSQL·Debezium 환경에서 첫 이벤트 처리 후 Offset 체크포인트 1을, 두 번째 이벤트 처리 후 체크포인트 2를 저장했다. replication slot은 최신 위치 `0/1940B90`에 둔 채 Debezium Offset만 과거 위치 `0/19409D0`로 되돌렸다. 복구 검증에서는 새 slot과 initial snapshot으로 이미 처리된 같은 Outbox 이벤트 10건을 다시 발행했다.

### 예상 문제

> slot보다 뒤처진 Offset에서 CDC를 계속 시작하면 서버가 이미 버린 변경 구간을 읽지 못해 조용한 이벤트 유실이 생길 수 있다. 반대로 새 slot과 snapshot으로 복구하면 이미 처리한 과거 이벤트가 다시 전달되어 Candidate 중복 저장이나 상태 퇴행이 발생할 수 있다.

### 복구 방안

> `offset.mismatch.strategy=trust_offset`로 읽을 수 없는 과거 위치를 오류로 차단하고, 로그와 LSN을 확인한 뒤 검증된 최신 Offset 체크포인트를 복원했다. 재전달은 Worker가 Generation의 현재 상태를 확인해 이미 READY인 작업을 SKIP하도록 처리했다.

### 정량 결과

> 실제 오류는 `Last recorded offset is no longer available on the server`였고 Health는 DOWN으로 전환됐다. 오류 탐지는 7.637초, 최신 Offset 복구는 7.393초였다. 과거 이벤트는 10건 발행·10건 전달·10건 ACK됐으며 Worker는 10건 모두 SKIP했다. READY는 10/10, Candidate는 1,200→1,200행, 이벤트 유실·후보 중복·DLQ 증가는 모두 0건이었다. 재전달 처리는 10.727초에 완료됐다.

### 문제 발견과 개선

> 첫 자동 실행은 시작 로그의 전략 설명을 실제 오류로 오인해 탐지 시간을 0.620초로 잘못 기록했다. 로그·Health·slot을 교차 검증해 문제를 발견했고, 실제 WARN/ERROR 문장만 탐지 조건으로 인정하도록 수정한 뒤 다시 실행했다. 첫 실행은 SUPERSEDED로 제외했고 공식 수치는 두 번째 실행의 7.637초다. Grafana에서는 짧은 정상 구간의 글자 잘림도 수정해 모든 상태명이 온전히 보이도록 했다.

### 한계

> 이 결과는 기존 개발 DB를 변경하지 않고 폐기 가능한 로컬 Docker 환경에서 수행한 10건 복구 정확성 실험이다. 부하 테스트가 아니며, Grafana 상태 전환에는 Prometheus 15초 수집 간격의 오차가 있다. 정확한 탐지·복구 시간은 Health endpoint와 오류 로그를 기준으로 했다.

## 21. 현재 포트폴리오에 바로 사용할 수 있는 실험 4 문안

### 제목

`Retry 분류와 DLQ 격리 — PASS`

### 한 문장 결론

> 일시 장애로 분류한 10건은 건당 최대 3회까지 실행해 실패 시도 30회·추가 Retry 20회를 기록한 뒤 DLQ로 격리했다. 복구 불가능한 오류 10건은 첫 실패에서 중단해 실패 시도 10회·추가 Retry 0회를 기록했다. 전용 DLQ 20건의 고유 Generation ID와 `x-death` 이력을 모두 확인했고 운영 DLQ는 167→167로 변화가 없었다.

### 장애 시뮬레이션

> 외부 장소 서비스의 일시 장애를 뜻하는 `PLACE_PROVIDER_UNAVAILABLE`과 잘못된 요청을 뜻하는 `PLACE_PROVIDER_REQUEST_REJECTED`를 결정적 실험 공급자로 각각 10건씩 발생시켰다. 두 시나리오는 실행별 전용 Queue·DLQ를 사용했고 Worker를 새로 띄워 Metric을 0부터 분리 측정했다.

### 예상 문제

> 모든 실패를 같은 방식으로 재시도하면 일시 장애에는 Retry가 부족해 복구 기회를 잃고, 복구 불가능한 오류에는 불필요한 호출과 처리 시간을 낭비할 수 있다. 실패 메시지를 Main Queue에 계속 돌려보내면 뒤의 정상 메시지 처리도 방해할 수 있다.

### 복구 방안

> 실패를 Retryable과 Non-Retryable로 분류했다. Retryable은 최대 3회로 제한하고, Non-Retryable은 첫 실패에서 중단했다. 정책이 끝난 메시지는 DB에 안정적인 실패 코드를 기록한 뒤 DLQ로 옮겨 자동 처리 흐름과 분리했다.

### 정량 결과

> Retryable 10건은 실패 시도 30회, 추가 Retry 20회, DB FAILED 10건, DLQ 10건이었다. Non-Retryable 10건은 실패 시도 10회, 추가 Retry 0회, DB FAILED 10건이었고 전용 DLQ는 누적 20건이 됐다. Candidate 저장과 READY 전환은 모두 0건이며 전용·운영 Main Queue는 최종 0건이었다. Worker 로그 30+10줄, Metric 30/20·10/0, DB 실패 코드 각 10건, DLQ 고유 ID 20개가 모두 일치했다.

### 문제 발견과 개선

> 첫 사전 실행은 이전 API 프로세스의 출력 파이프가 막혀 요청이 타임아웃됐다. DB에서 테스트 데이터가 생성되지 않았음을 확인하고 해당 Run을 PRECHECK_FAILED로 제외했다. API를 파일 로그 방식으로 재기동한 뒤 재실행했으며, 실패 시도·Retry Metric에 분류와 실패 코드 태그를 추가하고 모든 Attempt에 Generation ID와 시도 번호를 남겼다.

### 한계

> 이 결과는 로컬 Docker 환경의 시나리오별 10건 정확성 실험이다. 실제 외부 장애 대신 같은 예외 분류 경로의 결정적 실험 공급자를 사용했고, 시도당 1초 지연과 Worker 기동 시간이 포함되어 있어 처리 시간을 성능 수치로 일반화할 수 없다. DLQ 메시지를 수정해 정상 재처리하는 운영 절차는 별도 실험 범위다.

## 22. 현재 포트폴리오에 바로 사용할 수 있는 실험 5 문안

### 제목

`Stale Generation 자동 복구와 오래된 Worker 결과 차단 — PASS`

### 한 문장 결론

> Worker A가 Claim을 잡은 채 진행을 멈추자 Lease 만료 후 Recovery Scheduler가 10건을 다시 발행했고, Worker B가 새 Claim Version 2로 10건 모두 완료했다. 뒤늦게 돌아온 A의 Version 1 결과 10건은 Fencing으로 모두 차단되어 READY 10/10, Candidate 중복 0건을 유지했다.

### 장애 시뮬레이션

> Worker A가 테스트 요청 10건의 Claim Version 1을 얻은 직후 Candidate 결과 반환을 120초 지연했다. A의 Health는 UP이지만 RabbitMQ Unacked 10건과 DB의 후보 수집 중 상태가 유지되도록 했다. 실험 전용 Lease 15초가 만료된 뒤 Worker B와 단일 Recovery Scheduler를 실행했으며, B가 완료한 뒤 A의 오래된 결과 저장을 시도했다.

### 예상 문제

> Health만 보면 Worker A는 정상으로 보이지만 실제 작업은 멈춰 사용자가 결과를 받지 못할 수 있다. Lease 만료만 보고 다른 Worker가 재처리하더라도 기존 Worker의 늦은 결과를 허용하면 중복 Candidate가 생기거나 새 결과를 덮어쓸 수 있다.

### 복구 방안

> 제한 시간 안에 완료하지 못한 Generation만 Recovery Scheduler가 재발행한다. 복구 Worker는 Claim Version을 1에서 2로 올려 새 작업 소유권을 얻고, DB는 현재 Version과 일치하는 Worker의 결과만 저장한다. 오래된 Version 1 결과는 Fencing으로 거부한다.

### 정량 결과

> Worker A의 초기 Claim·Unacked·Lease 만료는 각각 10건이었다. Scheduler는 복구 메시지 10건을 발행했고 Worker B는 Claim Version 2로 10건 모두 성공했다. A의 늦은 결과는 Fencing 10건·SKIP 10건으로 모두 차단됐다. 최종 결과는 READY 10/10, FAILED 0, Candidate 1,200행, 중복 0행이었다. RabbitMQ Publish/Deliver/ACK는 20/20/20회였고 전용 DLQ는 0건, 운영 DLQ는 167→167로 변화가 없었다.

### 복구 시간

> 모든 Claim 확인 뒤 Lease 만료 10건을 관측하기까지 12.601초, Lease 만료 관측 후 READY 10/10까지 13.688초가 걸렸다. Worker B 시작을 기준으로 하면 13.687초였다. B가 완료한 뒤 A의 지연이 끝나 Fencing 10건이 확인되기까지는 91.627초가 걸렸다.

### 문제 발견과 개선

> Worker A는 논리적으로 멈췄지만 Health는 계속 UP이어서 Health Timeline만으로 장애를 설명할 수 없었다. 초기 Claim과 Recovery Claim, Recovery Publish, 오래된 Candidate 저장 Fencing을 별도 Metric으로 추가하고 Generation ID·Claim Version을 구조화 로그에 남겼다. Prometheus도 Worker A와 B를 별도 Job으로 수집해 어느 Worker가 어떤 역할을 했는지 분리했다.

### 한계

> 로컬 Docker 환경의 10건 복구 정확성 실험이며 부하 테스트가 아니다. 실제 네트워크 정지나 JVM Stop-the-world 대신 Candidate 반환을 120초 지연해 장애를 결정적으로 재현했다. 운영 Lease 15분은 실험에서만 15초로 줄였으며 여러 Scheduler 인스턴스의 동시 실행은 별도 검증이 필요하다.

## 23. 현재 포트폴리오에 바로 사용할 수 있는 실험 6 문안

### 제목

`RabbitMQ 중단 중 CDC 전달 위치 보호와 backlog 복구 — PASS`

### 한 문장 결론

> RabbitMQ가 28.541초 중단된 동안 Outbox 이벤트 10건은 DB에 보존되고 Debezium의 Offset과 Replication Slot은 전진하지 않았다. Broker 재기동 후 publish·deliver·ACK 10/10/10, READY 10/10을 확인했으며 이벤트 유실 0건, Candidate 중복 0건이었다.

### 예상 문제

> Debezium이 RabbitMQ 전송 실패를 성공으로 잘못 확정하면 Offset이 실제 전달 위치보다 앞서가고, DB에는 존재하지만 Queue에는 없는 조용한 이벤트 유실이 생길 수 있다. 반대로 무조건 재전송하면 중복 처리 가능성이 있으므로 전달 수와 최종 DB 중복도 함께 확인해야 한다.

### 복구 방안

> RabbitMQ 전송 실패 동안 Debezium Offset과 Replication Slot 확정 위치를 유지한다. Broker가 정상화되면 미확정 위치부터 이벤트를 다시 발행하고, Worker는 Generation 상태와 DB 제약으로 결과를 한 번만 반영한다. 전용 Audit Queue의 Generation ID와 DB ID를 비교해 단순 카운트 우연 일치를 배제한다.

### 정량 결과

> 중단 중 Outbox와 전달 대기는 각각 10건이었고 READY는 0건이었다. Debezium Sink 실패는 로그에서 54회 확인됐다. 복구 후 RabbitMQ publish·deliver·ACK는 10/10/10회, Audit 메시지와 고유 Generation ID는 10/10개였다. 최종 READY 10/10, FAILED 0, Candidate 1,200행, 장소·순위 중복 0행, 이벤트 유실 0건, 운영 DLQ 증가 0건이었다.

### 복구 시간

> RabbitMQ Start 후 Health UP까지 5.416초, Debezium 복구까지 10.324초, READY 10/10까지 15.905초가 걸렸다. Grafana의 DOWN/UP 경계는 Prometheus 15초 수집 간격의 오차가 있으므로 정확한 사건 시각은 자동화 타임라인을 함께 사용했다.

### 문제 발견과 개선

> 첫 데이터 Run은 Debezium 장애 상태를 Outbox 생성 전에 확인해 핵심 데이터 복구는 성공했지만 자동 판정 한 항목이 실패했다. 관측 순서를 Outbox 생성 뒤로 옮겨 재실행했고, Health Timeline만으로는 유실 여부를 증명할 수 없어 Offset SHA, Replication Slot, Audit Queue Generation ID를 추가했다. Grafana도 ① 장애 범위 → ② 대기 데이터 → ③ 전달 위치 → ④ 복구 전달 → ⑤ 최종 판정 순서로 바꾸고 용어 설명 패널을 넣었다.

### 한계

> 이 Run의 RabbitMQ 재전달은 0건이므로 메시지 유실 방지와 backlog 복구를 검증한 실험이다. 중복 메시지 멱등 처리는 실험 2와 3의 재전달·SKIP 결과로 설명한다. 로컬 Docker 10건 정확성 실험이며 장기 장애, 대량 부하, RabbitMQ 클러스터 장애는 별도 검증이 필요하다.

## 24. 현재 포트폴리오에 바로 사용할 수 있는 실험 7 문안

### 제목

`RabbitMQ 전달 후 DB 선점 전 Worker 종료와 미처리 메시지 복구 — PASS`

### 한 문장 결론

> RabbitMQ가 Worker A에 메시지 1건을 전달했지만 DB claim 전에 A를 종료하자 미확인 메시지가 Queue로 반환됐다. Worker B가 재전달 1건을 포함한 10건을 모두 최초 claim으로 처리해 READY 10/10, 이벤트 유실 0건, Candidate 중복 0건을 확인했다.

### 장애 시뮬레이션

> 전용 Worker A의 prefetch를 1로 두고 RabbitMQ delivery 직후 DB claim 전에 120초 대기하도록 했다. 테스트 Generation 10건을 만들고 Queue ready/unacked가 9/1, DB CREATED가 10, claim과 Candidate가 0인 순간 Worker A를 강제 종료했다. RabbitMQ가 ready/unacked를 10/0으로 되돌린 뒤 지연 없는 Worker B를 시작했다.

### 예상 문제

> ACK되지 않은 메시지가 Worker 종료와 함께 사라지거나, 재전달됐지만 DB에서 처리되지 않을 수 있다. 반대로 장애 위치가 claim 이후라면 두 Worker가 같은 결과를 저장해 Candidate 중복이나 상태 충돌이 생길 수 있다.

### 복구 방안

> RabbitMQ는 ACK되지 않은 메시지를 소비자 연결 종료 시 Queue에 다시 넣는다. Worker B는 반환된 1건을 `redelivered=true`로 받고, Worker A가 claim하지 않았으므로 SKIP이 아니라 최초 claim으로 처리한다. Generation 상태와 DB 고유 제약으로 결과는 Generation마다 한 세트만 저장한다.

### 정량 결과

> 종료 직전 delivery 1, ready/unacked 9/1, CREATED 10, claim 0, Candidate 0이었다. 종료 후 Queue는 10/0으로 돌아왔고 재큐잉 감지에는 4.563초가 걸렸다. 복구 후 publish/deliver/ACK/redelivery는 10/11/10/1회, Worker B의 최초 claim·성공은 10/10회, SKIP은 0회였다. 최종 READY 10/10, Candidate 1,200행, 유실·중복·DLQ 증가 모두 0이었다.

### 복구 시간

> Worker B 시작 후 Health UP까지 11.955초, 10건 전체 처리까지 14.074초가 걸렸다. Grafana의 Worker `정상 → 중단 → 정상` 경계에는 Prometheus 15초 수집 오차가 있으므로 정확한 재큐잉 4.563초는 RabbitMQ Management API와 자동화 타임라인을 기준으로 했다.

### 문제 발견과 개선

> Worker 포트가 열리기 전 Health 연결 지연을 막기 위해 TCP 준비 확인을 추가했다. 새 여행 생성의 외부 장소 상세 API 지연은 메시징 실험과 분리해 완료된 여행 10개를 재사용했다. 15초 Prometheus 수집이 약 5초의 `unacked=1`을 놓친 사실을 숨기지 않고 RabbitMQ 원본 스냅샷을 함께 제시했다. Grafana는 ① 장애 범위 → ② 종료 직전 경계 → ③ 재큐잉 → ④ 재기동 처리 → ⑤ 최종 판정 순서와 쉬운 용어 설명으로 구성했다.

### 한계

> 로컬 Docker 10건 정확성 실험이며 부하 테스트가 아니다. 실험 전용 지연 훅으로 DB claim 전 종료 위치를 결정적으로 만들었고 RabbitMQ 단일 노드와 단일 소비자 전환을 검증했다. Debezium 단독의 멱등성 결과로 표현하지 말고 RabbitMQ ACK·재전달과 Worker DB 상태·제약의 결합 결과로 설명해야 한다.
